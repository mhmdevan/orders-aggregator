# Orders Aggregator

Сервис статистики заказов на TypeScript и PostgreSQL. Загружает заказы из внешнего API, принимает обновления через webhook и рассчитывает ежедневные суммы по клиентам с учётом скидок и исторических правил их таймзон.

**Рекомендуемое название репозитория:** `orders-aggregator`.

## Возможности

- Полная синхронизация заказов с пагинацией, ограничением частоты запросов и повторными попытками.
- Обработка повторных, устаревших и одновременно поступающих обновлений.
- Расчёт суммы до скидки, фактической оплаты и скидки по каждому дню.
- Корректная группировка при переходах на летнее и зимнее время.
- Совместимость со старыми заказами без полей скидки.
- Хранение денежных сумм в целых копейках и времени в UTC.

Описание исправлений, допущений и проведённой проверки: [SOLUTION.md](SOLUTION.md). Исходные требования: [TASK.md](TASK.md).

## Стек

Node.js, TypeScript, Fastify, PostgreSQL 16, Zod, Vitest. Работа с PostgreSQL — через `pg`, миграции — SQL-файлы.

## Требования

- Node.js 20+ и npm; решение проверено на Node.js 22.15.1.
- Docker с Docker Compose.
- Предоставленный образ внешнего API: `orders-mock-arm64.tar.gz` или `orders-mock-amd64.tar.gz`. Образы не входят в архив решения.
- Доступные порты 3000, 4000 и 55432 при стандартных настройках `.env.example`.

Все команды ниже выполняются из корня приложения: папки `app` в архиве или корня репозитория, если в него загружено содержимое `app`.

## Быстрый запуск

### 1. Загрузить образ внешнего API

Определите архитектуру:

```bash
uname -m
```

Загрузите **один** подходящий образ. В примерах файл расположен рядом с папкой приложения; при другом расположении укажите свой путь.

Для Apple Silicon / ARM64:

```bash
docker load -i ../orders-mock-arm64.tar.gz
```

Для x86_64 / AMD64:

```bash
docker load -i ../orders-mock-amd64.tar.gz
```

### 2. Настроить окружение

При первом запуске создайте локальный файл настроек:

```bash
cp .env.example .env
```

Экспортируйте переменные в текущий терминал. Команды приведены для bash/zsh:

```bash
set -a
source .env
set +a
```

Node автоматически не читает `.env`, поэтому повторяйте экспорт в каждом терминале, где запускаете сервис, миграции или тесты.

| Переменная | Значение в `.env.example` | Назначение |
|---|---|---|
| `POSTGRES_PORT` | `55432` | Порт PostgreSQL на хосте |
| `DATABASE_URL` | `postgres://postgres:postgres@127.0.0.1:55432/orders` | Основная БД |
| `TEST_DATABASE_URL` | `postgres://postgres:postgres@127.0.0.1:55432/orders_test` | Отдельная БД тестов |
| `ORDERS_API_URL` | `http://localhost:4000` | Адрес внешнего API |
| `PORT` | `3000` | Порт приложения |

Если меняете `POSTGRES_PORT`, измените порт и в обеих строках подключения.

### 3. Запустить PostgreSQL и внешний API

```bash
docker compose -p orders-task-app up -d
```

Compose запускает PostgreSQL, создаёт БД `orders` и `orders_test`, а также поднимает внешний API на порту 4000. Проверьте готовность PostgreSQL:

```bash
docker compose -p orders-task-app exec -T postgres pg_isready -U postgres -d orders
```

Продолжайте после ответа `accepting connections`.

### 4. Установить зависимости и запустить приложение

```bash
npm ci
npm run dev
```

Миграции применяются автоматически при запуске. Для отдельного применения доступна команда `npm run migrate`.

Сервис доступен по адресу [http://localhost:3000](http://localhost:3000). Проверка работоспособности из другого терминала:

```bash
curl --fail-with-body -sS http://localhost:3000/health
```

Ответ:

```json
{ "status": "ok" }
```

Для запуска без наблюдения за изменениями используйте `npm start`.

## Получение результата задания

Используйте чистую основную БД и запущенное приложение. В отдельном терминале перейдите в папку приложения и экспортируйте `.env`, как описано выше.

Выполните команды **последовательно**, дожидаясь завершения каждой.

### 1. Полностью синхронизировать заказы

```bash
curl --fail-with-body -sS -X POST http://localhost:3000/sync
```

Результат фактического проверочного запуска:

```json
{
  "pages": 52,
  "received": 5030,
  "applied": 5030,
  "stale": 0,
  "invalid": 0
}
```

### 2. Отправить обновления через webhook

```bash
docker compose -p orders-task-app run --rm orders-api webhooks --target http://host.docker.internal:3000/webhooks/order
```

В проверочном запуске отправлено 92 события; все получили HTTP 200.

### 3. Сохранить итоговый отчёт

```bash
curl --fail-with-body -sS 'http://localhost:3000/customers/c_7/daily-totals?from=2026-03-27&to=2026-03-31' > result.json
```

Готовый результат: [result.json](result.json). Он получен после завершения sync и всех webhook.

### 4. Проверить результат независимым расчётом

```bash
npm run verify:result
```

Команда сравнивает `result.json` и текущий HTTP-ответ с отдельным SQL-расчётом PostgreSQL через `AT TIME ZONE` и точные числовые суммы. При расхождении завершается с ошибкой.

## API приложения

| Метод | Путь | Результат |
|---|---|---|
| `GET` | `/health` | Проверка работоспособности |
| `POST` | `/sync` | Полная загрузка заказов; ответ после завершения со счётчиками обработки |
| `POST` | `/webhooks/order` | Применение версии заказа; результат `created`, `updated` или `stale` |
| `GET` | `/customers/:id/daily-totals?from=YYYY-MM-DD&to=YYYY-MM-DD` | Ежедневные суммы по клиенту, включая обе границы периода |

Пример запроса отчёта после воспроизведения результата:

```bash
curl --fail-with-body -sS 'http://localhost:3000/customers/c_7/daily-totals?from=2026-03-27&to=2026-03-27'
```

Ответ:

```json
[
  {
    "date": "2026-03-27",
    "total": 24736,
    "gross": 24736,
    "discount": 4880.49,
    "net": 19855.51
  }
]
```

### Правила расчёта

- Учитываются только заказы со статусом `paid`.
- День определяется по `createdAt` в таймзоне клиента с учётом смещения именно в момент создания заказа.
- `gross` — сумма до скидки; `total = gross` для обратной совместимости.
- `net` — фактически оплаченная сумма из `amountPaid`.
- `discount = gross - net`; все расчёты выполняются в копейках, ответ возвращается в рублях.
- Для старых заказов без обоих полей скидки принято `net = gross`.
- Положительный процент без `amountPaid` считается неполными данными; явная нулевая оплата допускается.
- Дни без оплат возвращаются с нулевыми суммами.

Ошибки бизнес-логики имеют формат:

```json
{
  "error": "bad_request",
  "message": "from and to must be dates in YYYY-MM-DD format"
}
```

Некорректные входные данные возвращают 400, неизвестный клиент — 404, ошибки обращения к внешнему API — 502.

## Формат внешнего API

- `GET /orders?cursor=<string>&limit=<1..100>` возвращает `{ items, nextCursor }`; лимит API — 5 запросов в секунду.
- `GET /customers/:id` возвращает `{ id, timezone }`, где `timezone` — имя IANA, например `Europe/Berlin`.
- Webhook отправляет заказ в теле `POST /webhooks/order`; возможны повторы и нарушение порядка доставки.

Фактически поддерживаемые входные данные заказа:

```ts
type ExternalOrder = {
  id: string;
  customerId: string;
  amount: number | string;           // рубли до скидки
  discountPercent?: number | string; // процент скидки
  amountPaid?: number | string;      // фактически оплачено, рубли
  status: "pending" | "paid" | "refunded";
  createdAt: string;                 // ISO 8601
  updatedAt: string;                 // версия заказа
};
```

Согласно контракту, время без обозначения зоны трактуется как UTC. Источник фактической оплаты — `amountPaid`; процент не используется для повторного вычисления платежа.

## Тесты и проверка типов

При запущенном PostgreSQL и экспортированных переменных `.env`:

```bash
npm test
npm run typecheck
```

Интеграционные тесты работают с настоящим PostgreSQL и подменяют внешний API фейком. Очищается только тестовая БД `orders_test`.

Проверено **57 тестов в пяти файлах**: скидки, точность копеек, старые заказы, границы периода, переходы времени, версии webhook, конкурентная доставка и валидация. TypeScript проходит без ошибок.

Артефакты фактического запуска находятся в [verification](verification/), подробности проверки — в [SOLUTION.md](SOLUTION.md).
